# Capacity

Generated by `ifp sweep`: one model server process (v2, 30 features, one instance per request), a closed-loop client holding a fixed number of requests in flight for 5 s per level. Client and server shared one two-core development machine, so at high concurrency the client competes with the server for CPU and throughput falls instead of levelling off. Absolute numbers depend on the hardware; the method is what carries over.

**Target: 8 requests in flight per pod**, the highest level that still delivers 90% of the best throughput with a p95 within 50% of the 300 ms latency objective. Past it, requests only queue. The HorizontalPodAutoscaler scales on `inference_inflight_requests` with this target (`deploy/k8s/base/autoscaling.yaml`); the server's admission limit (64) sits well above it, so bursts queue briefly instead of failing while new pods start.
